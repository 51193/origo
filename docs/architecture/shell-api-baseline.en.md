# Shell API Baseline and Gate

> [↑ Back to architecture](README.en.md) · [↔ shell/kernel boundary](shell-kernel-boundary.en.md) · [↔ API classification](shell-api-classification.en.md)

This document defines the 0.1.0 shell API baseline gate: a tracked Roslyn inventory produces deterministic JSON from a real Release build, and every unapproved shell API addition, removal, or signature change must update the baseline in the same reviewed change. Signature changes include generic variance and the whitelisted nullable-flow attributes, because both change what a nullable-enabled consumer can compile.

## Scope

- The inventory covers the exported surface of the `Origo.Core.Contracts`, `Origo.Core`, `Origo.GodotAdapter`, and `Origo.ConsoleBridge` shell assemblies.
- Exported types (including C# type modifiers such as `static`/`sealed`/`abstract`/`readonly`/`ref` and enum/struct/delegate kinds), public/protected members, signatures, nullable reference annotations, generic variance (`out`/`in`), default values, generic constraints, `init`/`set` accessors, extension-method `this` parameters, members generated by the Source Generator, and generated nested Godot signal types all enter the baseline.
- The whitelisted nullable-flow attributes (`NotNullWhen`, `MaybeNullWhen`, `NotNull`, `MaybeNull`, `AllowNull`, `DisallowNull`, `NotNullIfNotNull`, `MemberNotNull`, `MemberNotNullWhen`) are rendered explicitly on the parameter or member they annotate, using fully-qualified `System.Diagnostics.CodeAnalysis.*` names and a deterministic ordinal order. Other attributes are not recorded, so unrelated metadata such as `Obsolete` does not freeze as a contract.
- `Origo.Core.Kernel` is the kernel implementation package and stays out of the baseline; the tool fails explicitly when an exported signature references a kernel assembly type. `Origo.ConsoleBridge` is also part of the member-level baseline; its shell-only dependency and packaged consumption are additionally covered by #42.
- Reviewed pre-0.1 breaking changes are declared explicitly in `tools/ApiInventoryTool/shell-api-approved-breaks.json`; the previous-package comparison filters only those declared removals, and the gate still fails on undeclared changes, invalid entries, and dormant approvals, while obsolete approvals are reported for cleanup (see [Approved Breaking Changes](#approved-breaking-changes)).

## Gate Execution

`scripts/bash/api-inventory.sh`:

1. Builds the four shell projects in Release; the repository-wide warnings-as-errors setting stops the gate before inventory generation on any compiler or Source Generator diagnostic error.
2. Runs the `tools/ApiInventoryTool` Roslyn metadata inventory.
3. In `verify` mode, compares each API line with `tools/ApiInventoryTool/shell-api-baseline.json`; any addition, removal, or signature change exits non-zero with the diff and the regeneration command. `verify` always compares the enriched schema-version-2 line shape; when the schema versions differ, the previous-package comparison projects both sides onto the version-1 line shape instead (see [Baseline and Ownership](#baseline-and-ownership)).
4. `generate` mode is for approved changes: it rewrites the baseline JSON, which must be reviewed and committed with the implementation.
5. When `tools/ApiInventoryTool/shell-api-approved-breaks.json` exists, the previous-package comparison passes it to `compare --approved-breaks`; a break declared there is accepted only when it exactly matches a reported removed-or-changed line. Duplicate, dormant, and wrong-assembly entries fail; obsolete entries are reported for cleanup but do not fail the gate.

The script runs in normal CI (Ubuntu/macOS/Windows), `scripts/bash/ci.sh`, and the Release workflow. The normal CI checkout fetches full history and tags, and a dedicated step fails if no formal release tag is visible; without that, a depth-1 checkout would silently skip the previous-package comparison. Baseline resolution is fail-closed: when formal release tags exist but no usable previous baseline can be resolved (a baseline-bearing tag that is neither an ancestor nor the recognized metadata-only release commit), `scripts/bash/find-previous-api-baseline.sh` reports the inconsistency and the gate aborts instead of silently disabling previous-package validation. A formal release tag newer than the source version is skipped by the version ceiling: the helper uses the newest older baseline and aborts only when no such older baseline remains. The trade-off of that skip is that a line added in the skipped release and removed again before the current source is invisible to previous-package comparison; the committed-baseline `verify` gate still enforces same-schema changes, and advancing the development baseline past the latest release removes the skip. The only silent skip is the documented first-release state, where every eligible formal release predates the baseline tool. An unapproved change therefore cannot pass any of those gates.

## Baseline and Ownership

| Item | Description |
|------|-------------|
| Baseline file | `tools/ApiInventoryTool/shell-api-baseline.json` |
| Produced by | `bash scripts/bash/api-inventory.sh generate`; never hand-written |
| Owner | Framework maintainer, who confirms every diff is an intentional shell contract change during review |
| Update condition | An approved new shell API, removal, or signature change with tests and English documentation updated in the same change |
| Schema version | `schemaVersion: 2`; version 2 records generic variance and nullable-flow attributes. A bump must teach `InventoryComparer.ComparePrevious` to project both sides onto the older line shape instead of reporting false removals |
| Approved-breaks file | `tools/ApiInventoryTool/shell-api-approved-breaks.json`; `{ "breaks": [ { "assembly", "api", "reason" } ] }`, hand-maintained review input (not generated) |
| Approved-break review | Each entry names one exact previous-baseline line and a non-empty reason. A dormant entry (the line is still in the previous baseline but approves nothing) fails; an obsolete entry (a newer release already removed the line) is ignored and reported so it can be deleted |
| Kernel impact | Kernel implementation additions/removals do not change the baseline; a reference leak fails immediately |

There is no previous stable shell package before the first 0.1.0 release, so previous-package validation is explicitly skipped with an explanation. Afterwards, when `ORIGO_PREVIOUS_API_BASELINE` is not set, `scripts/bash/api-inventory.sh` auto-detects the newest formal release tag not newer than the current source version, excluding the tag on the current commit and the current release tag supplied through `ORIGO_CURRENT_RELEASE_TAG`, and extracts its `shell-api-baseline.json`; the explicit environment variable overrides auto-detection. A tag-only release commit is a metadata-only child of the main commit it was cut from, so the helper accepts such a tag even when it is not an ancestor of HEAD. The previous-package compare fails removals and signature changes while allowing backward-compatible additions. Pre-0.1 breaking changes approved by the maintainer are the only exception: they are filtered only when declared in the approved-breaks file (see [Approved Breaking Changes](#approved-breaking-changes)); 0.1.x promises source/behavior compatibility for everything that is not explicitly approved, not binary compatibility.

Version-1 and version-2 baselines are compared through a projection: when the schema versions differ, both sides are reduced to the version-1 line shape (nullable-flow attribute segments and generic variance markers removed) before the removal check. Without that projection the enriched lines of a version-2 baseline would read as false removals against the version-1 baseline carried by the previous Release package. The projection intentionally has a one-release blind spot: a change that only touches generic variance or a nullable-flow attribute is not reported by previous-package validation while the previous Release baseline is still version 1. The committed-baseline `verify` comparison runs against the same-schema tracked baseline and enforces the enriched shape immediately, so the blind spot cannot hide an unapproved change from normal CI or the Release workflow.

## Approved Breaking Changes

Pre-0.1 breaking changes are allowed when the maintainer approves them, but they stay visible in review instead of being suppressed. The tracked file `tools/ApiInventoryTool/shell-api-approved-breaks.json` declares each approved break as one exact previous-baseline line:

```json
{
  "breaks": [
    {
      "assembly": "Origo.Core.Contracts",
      "api": "M:Origo.Core.Abstractions.Blackboard.IBlackboard.(bool found, T value) TryGet<T>(string key)",
      "reason": "Pre-0.1 nullable annotation correction; no external consumers exist yet."
    }
  ]
}
```

`api` must be the exact line the comparison reports as removed or changed (the previous baseline's line, including the `M:`/`P:`/`T:` prefix), `assembly` is the shell assembly it belongs to, and `reason` must be non-empty. An empty `breaks` array is the normal state. A compatible addition can still change a recorded line — for example adding `IDisposable` to `OrigoHost` changes its type line from `Origo.Core.Abstractions.Runtime.IOrigoFrameDriver` to `..., System.IDisposable` — so the changed previous line is approved exactly like a removal even though the addition itself is source-compatible.

`compare` loads the file, classifies every entry against the projected previous baseline, and reports the applied and obsolete counts. The policy is deliberately strict, deterministic, and release-aware:

- an undeclared removal or signature change still fails;
- an approval that exactly matches a reported failure is applied;
- a **dormant** approval (its line is still part of the previous baseline, so it suppresses nothing) fails, so a suppression cannot silently outlive or misstate the change it was written for;
- an **obsolete** approval (its line is already gone from the previous baseline because the release that carries the change became the previous release) is ignored and reported for cleanup — this keeps the first post-release push green while still surfacing out-of-date entries in the approval file. Obsolete approvals must be deleted after the release that makes them obsolete; until then an ignored entry can re-arm and approve the same signature if a later change reintroduces it;
- a wrong-assembly approval fails: an entry whose line belongs to a different shell assembly never matches;
- missing-assembly failures cannot be approved (there is no line to match);
- duplicate entries, empty fields, and a missing or malformed file exit non-zero with the offending entry identified.

Every entry is reviewed as part of the same change as the API break, and `verify` still compares against the same-schema tracked baseline, so the local/CI gate continues to enforce the real surface before and after the previous-package comparison.

## Failure Semantics

- Build failure or Source Generator diagnostic error: the script exits before inventory generation and never leaves a partial baseline.
- Missing assembly, missing reference directory, unresolved reference, or an exported signature referencing a kernel type: the tool reports an explicit error and exits non-zero without writing `generate` output. Kernel-reference checks recurse through generic type arguments, array/pointer/function-pointer elements, indexer parameters, and method generic constraints.
- Missing baseline file: `verify` fails explicitly and instructs the developer to generate the baseline in the same reviewed change.
- Approved-breaks file: a malformed, duplicate, empty-field, dormant, or wrong-assembly entry fails `compare` explicitly; obsolete approvals are reported for cleanup but do not fail; an approved entry never suppresses an entry it does not exactly match.
- Determinism: JSON is ordered by assembly name and ordinal API lines with normalized LF line endings, so repeated runs are byte-identical; nullable-flow attributes are sorted ordinally and rendered with fully-qualified names. `ApiInventoryTool.Tests` covers determinism (including multi-assembly name ordering), addition/removal detection, previous-package rules (including version-1 projection), kernel-reference rejection, unresolved-reference rejection, and command-line failure paths; the per-method breakdown is under [Test Capability](#test-capability) below.

## Design Decisions

### Why a JSON Baseline Before an Analyzer

The 0.1.0 shell surface is still stabilizing. A tracked JSON baseline gives a reviewable full diff in normal CI and allows evaluating a `PublicApiAnalyzers`-style gate after the baseline stabilizes; introducing an analyzer first would freeze undecided implementation details as diagnostic noise.

### Why Additions Also Require a Baseline Update

The gate means "the shell surface consumers see can only change intentionally", not "no evolution". An added API changes the consumer contract just as a removal does, so it requires explicit review and a same-commit baseline update.

### Why Release Tags Are Selected by Version, Not Ancestry

A release tag points at a tag-only release commit whose parent is the main commit
the release was cut from. That commit is a sibling of the next release commit, not
its ancestor. Requiring ancestry alone would silently skip the immediately
preceding release and compare the new surface against an older baseline, which
could let a removal introduced in the skipped release pass. The helper therefore
selects the newest formal tag not newer than the current source version and accepts a
non-ancestor tag only when it is the known metadata-only `chore(release): sync
version stamps to vX.Y.Z` commit whose parent is reachable from HEAD.

### Why Generic Variance and Nullable-Flow Attributes Are Recorded

A consumer recompiles against the shell packages, so source compatibility includes what the compiler checks at the call site. Removing `out` from a generic interface parameter breaks assignment compatibility (`ILogger<Derived>` to `ILogger<Base>`); removing `[NotNullWhen(true)]` removes a nullable-flow guarantee and can turn consumer code into warnings or errors. `SymbolDisplayFormat` cannot emit attributes, so the tool renders the whitelisted ones explicitly; recording every attribute would freeze unrelated metadata instead of the consumer contract.

### Why Approved Breaks Are Explicit and Release-Aware

A pre-0.1 break still changes what consumers compile, so suppressing it must be visible: the suppression lives in a tracked JSON file where each line carries an exact assembly+api match and a reviewer-facing reason, and the diff of that file is reviewed with the break. The release-aware classification keeps the file honest across release boundaries: a dormant approval (the previous baseline still contains the line) fails because it approves nothing, while an obsolete approval (the release that carried the change is now the previous baseline) is ignored and reported for cleanup instead of turning the first post-release push red. Missing-assembly failures and undeclared removals remain hard failures; only exact declared lines are filtered.

### Why the Baseline Excludes Kernel Assemblies

Kernel packages make no consumer compatibility promise in 0.1.x; including the kernel export surface would freeze implementation details as a contract. A shell signature referencing a kernel type is a compile-surface leak, so it fails instead of being recorded as an allowed difference.
