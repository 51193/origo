# 按需 Skills：触发、契约、脚本边界与验收

> [↑ 回到调查索引](README.zh.md)

## 事实与适用范围

调查日期2026-09-18，基线`cdba5e4`；本报告提出候选技能，没有创建或安装skill。`git ls-files .agents .codex`没有返回仓库跟踪文件；当前会话的个人/系统skills不等于Origo发行物。

[官方 Build skills](https://developers.openai.com/codex/skills/) 描述渐进披露：先提供名称/描述，决定使用时才加载全文；支持显式调用和描述匹配。可复用技能包含说明、资源和可选脚本。这提供按需上下文机制，但不保证自动匹配总正确。

**推断：** skills能降低重复程序说明，不能修复API本身歧义，也不能替代可执行验证。对于游戏引擎，应优先包装“做出可运行且可验证的游戏功能”；仅包装引擎维护流程不能直接实现用户的游戏开发价值。

## 两类技能与触发正反例

| 候选skill | 应触发的任务 | 不应触发的任务 | 关键输出 |
|---|---|---|---|
| `origo-game-strategy` | “实现生命值、受伤和死亡，并测试恢复” | 只解释SND；只修改引擎发布版本 | 策略/Data/模板改动、契约链、行为及恢复证据 |
| `origo-game-debug` | “定位点击失效/实体不动，用运行结果验证” | 仅修文档链接；仅做静态审阅 | 构建/seed/环境标识、复现步骤、前后状态和GUI适用性 |
| `origo-engine-regression` | Core/Adapter明确缺陷，需真实路径红→绿 | 对未知设计做猜测重构；只读评估 | 症状、真实路径、未修复红证据、相同测试绿证据、兄弟路径 |
| `origo-docsync` | 修改镜像接口/文件/设计或使用文档 | 只搜索文档；仅内部实现且没有结构/设计变化 | 双语权威更新、generate/validate结果、生成文件清单 |
| `origo-release` | 明确准备或执行正式发布 | 任意源码任务；一般Changelog编辑 | 版本/元数据对齐、既有完整发布验证证据 |

描述应先写任务动词与对象，再写容易混淆的排除项。“所有Origo相关任务都使用”会吸走其他任务；“涉及Save即可触发正式发布”也过宽。多个skill可同任务使用，但步骤和门禁来自唯一权威，避免两个技能给出不同完成定义。

所有技能保留full-chain、历史理解、single access path和fail-fast。比如调试不能通过直接调内部flush/生命周期钩子伪造成功；回归不能只断言内部方法而遗漏业务症状。某些设计问题按AGENTS必须询问维护者，技能不得让Agent自称已证明。

## 输入与输出契约

以`origo-game-strategy`为例，输入至少包括：游戏仓库和使用的Origo版本、功能验收（如hp归零请求死亡）、实体/策略索引和已有Data类型、恢复语义、目标宿主、允许修改范围。可由资料推导的值先读取；缺少影响行为的定义再询问。不能默填未知策略索引、数据键或保存格式。

输出不只是代码，需包含：读取的权威及协作者、改动文件、策略共享状态/生命周期配对检查、真实行为断言、存档恢复断言、执行命令与状态、未支持场景和剩余失败。模板可辅助创建结构，但不能固定把业务状态初始化放到`AfterLoad`： [生命周期文档](../../usage/strategy-lifecycle.zh.md) 明确这会覆盖存档状态。

以`origo-game-debug`为例，输入需包括复现条件、构建、seed/初始状态及可用宿主。输出区分“模拟Button信号成功”“真实鼠标输入成功”“状态符合预期”。[策略测试](../../usage/strategy-testing.zh.md) 不支持节点和多实体完整交互时，应路由到宿主/集成场景，不把不支持伪装成通过。

## Skill与确定性脚本的边界

| 适合skill中的判断 | 应由脚本/工具执行的确定性工作 |
|---|---|
| 判断缺陷、设计或资料未知；确定协作者和真实路径 | 解析SDK、版本、路径、项目依赖和测试选择 |
| 选择无节点harness、完整Core宿主或GUI场景 | 构建、运行测试、收集退出状态和产物 |
| 解释玩法验收及异常意义 | DocSync生成/验证、格式、commit lint |
| 根据失败证据扩展阅读链 | 帧/seed/存档/构建标识采集、命令参数校验 |

skill调用现有权威脚本；不要复制安装、编译、测试、生成命令实现成第二条链。需要稳定执行的工作应提供显式输入、非零失败状态和机器可读结果，skill负责解释与决策。skill本身不是测试框架，也不是工具授权凭证。

## 压缩、失败与跨Agent支持

索引名称和描述也有上下文成本，skill越多不一定越好。正文保持触发、流程、不可违反的约束、输出合同；大量例子和模式放references，按条件读取，不要求全读。对长任务，应保存基线、已读链、行为验收和运行结果以支持恢复；不能依靠压缩后的聊天记忆证明测试通过。

失配可通过显式调用或手动读取权威流程恢复。文件缺失、SDK/宿主不可用或接口不支持时明确失败并记录下一动作，不自动降低验证标准。工具不支持skills时仍应能从根任务矩阵找到相同权威文档和脚本；只有包装器丢失，工程合同不应丢失。

开放skill格式不意味着所有Agent都支持相同目录发现、描述匹配、MCP依赖或权限语义。Origo发布包要声明支持的Agent/版本、OS、宿主、工具与依赖，并分别验证；避免宣称“一份skill全Agent通用”。引擎消费方应获得使用流程和工具合同，引擎维护skill无需强制随游戏项目加载。

## 维护成本与实验

每个技能指定owner和权威来源，尽量不抄API签名。模块/命令变更要检查触发描述、引用和产物合同；同名技能、个人覆盖、错误启动目录都是应测试的发现问题。保留少量高价值技能，使用路径有效性、描述路由和真实任务回放检查其维护质量。

先选择重复且风险明确的策略开发与回归两项做试点。准备显式调用、自然语言隐式调用、模糊任务、负例、范围扩大、缺宿主六类输入；记录触发precision/recall、正确路线、输出完整性和违规。再做A/B：A保留当前文档路线，B使用按需skill；固定任务/模型/预算，独立验收游戏结果和隐藏测试，记录人类介入与上下文/执行成本。触发正确而游戏结果错误仍为失败。

门槛应在试验前约定：关键安全/生命周期规则不得下降，行为通过率不降低，查找或验证耗时应有实际收益；同时核算更新skills所花维护时间。根路由的迁移配套见 [根指令研究](root-instructions.zh.md)，上下文与运行证据为何同样重要见 [OpenAI Harness调查](openai-harness.zh.md)。
