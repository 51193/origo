## “地图”的机制

地图需要回答五个问题：任务属于哪个领域；下一步去哪个权威入口；必须理解哪些协作者；怎样验证结果；失败如何定位。百科式入口倾向于预先提供所有答案。地图则让 Agent 先取得路由，再读取任务所需细节，同时保留不能忘记的全局约束。

这里有三个独立层次：根指令负责持续约束和导航，模块文档解释契约与理由，脚本和运行时工具提供当前可验证事实。把长指令挪到一个要求每次完整读取的链接，并没有实现渐进披露。反过来，只缩短入口却不给路由，也会让 Agent 猜测或漏读。

**推断：** 对 Origo，优化目标应是“更低的信息查找成本、相同或更高的契约遵守率”。不能以少读上下游、跳过历史或绕过编排来换速度。OpenAI 案例对合并门禁的取舍也不适合直接移植；Origo 的严格存档、生命周期和覆盖率要求继续有效。

## 三个具体任务

### 为游戏加入受伤死亡策略

当前 [Agent Reference](../../usage/agent-reference.zh.md) 汇集黑板、文件、存档、会话、状态机和策略样例。真正关键的知识是共享策略不能保存每实体可变状态，Data是状态来源，死亡应通过 `entity.OwningSession.RequestKillEntity`，由框架处理帧末和钩子。

**提案：** 游戏开发入口直接路由到实体模型、生命周期、策略测试，以及死亡契约涉及的会话资料。Agent先列相关设施，再读取相应模块，而不是从完整参考中猜测哪些内容适用。若涉及跨实体观察或读档，路由必须扩展到对应契约。引擎维护与消费引擎的游戏开发流程应分别标明，不能把发布Origo的步骤强加给游戏项目。

### “按钮存在，但点击没有开始游戏”

已有 `tree_debug` 能确认节点路径，`press_button` 能验证信号后的游戏行为。不过 [GodotAdapter 注意事项](../../Origo.GodotAdapter/README.zh.md) 指出全屏Control的鼠标过滤可吞掉3D输入，headless视口为零。只发 `Pressed` 信号会绕过真实点击位置、GUI消费和输入阶段。

**提案：** 验证矩阵明确区分信号路径、真实GUI输入、游戏状态三个检查；附GUI截图、坐标、前后状态、构建标识。将“能看见节点”与“玩家能点击”分成独立验收项。工作目录隔离只是开始，还要隔离端口、`user://`状态、日志和存档，避免并行Agent相互干扰。

### “自动存档成功了，但重启后的数据不对”

[策略测试](../../usage/strategy-testing.zh.md) 的 `SaveRequests` 只是请求记录；文档明确该harness不支持完整后台会话和节点。它不能证明磁盘写入完整、快照一致或重启恢复正确。

**提案：** 将测试证据分成请求、完整存档管线、宿主恢复三层；真实路径回归经公共Save入口和帧驱动触发，不能手动调用内部flush模拟完成。运行记录携带seed、帧号、存档根、载荷/构建标识，并在恢复后检查行为和状态。先定义可测断言，再决定是否需要额外工具接口。

## 学习顺序与验收

先建立任务路由和两类使用者入口，再使任务环境可复现和可查询，最后让反复发生的失败转成检查或文档。规则的名字和目录结构无需照搬OpenAI；关键是Agent能自主找到并验证所需事实。

选择至少策略编写、真实点击、存档恢复、Core维护四类任务，固定Agent和预算，比较当前入口与提案入口。记录阅读文件及上下文量、第一次正确验证耗时、人工提示次数、架构违规、隐藏测试通过与恢复一致性。没有这些证据，不宣称地图方案提高成功率。根指令与skills的具体方案见 [根指令研究](root-instructions.zh.md) 和 [skills研究](skills.zh.md)。
