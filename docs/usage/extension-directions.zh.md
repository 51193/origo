# 扩展方向与暂缓设计

> [↑ 回到 usage](README.zh.md)

> **性质说明**：本文档记录头脑风暴产生的备选设计方向，均属于“已讨论、未进入实现、暂缓”的思考。它们不是当前框架能力，不构成路线图承诺，也不改变任何现有接口语义。本文的价值在于把“为什么不这样做”的完整权衡留在文档里：当开发者或 agent 遇到相关问题时，可以先看到现状的设计边界，再判断收益是否已经高到值得重新评估；当收益条件成熟时，也可以直接拾起这些已经想过的骨架，而不是从零重新发明。

阅读本文前，应先理解当前现状：[架构总览](architecture-overview.zh.md)、[SND 实体模型](snd-entity-model.zh.md)、[策略生命周期](strategy-lifecycle.zh.md)、[设计模式](design-patterns.zh.md)。

## 方向速览

| 方向 | 关联现状 | 暂缓核心原因 | 重新评估信号 |
|------|----------|--------------|--------------|
| 统一树形命名空间 | `DataSourceNode` 树 + `IDataSourceIoGateway` 文件内容边界 | 本地同步读足够，远端异步访问会阻塞帧；统一命名空间会牵动所有 I/O 契约 | 需要把本地文件、存档、网络资源用同一种访问协议处理 |
| 实体级并发 | 单线程帧模型 + 无状态策略池 | 跨实体读写、观察者通知、依赖与销毁语义都要重新定义，成本极高 | 性能分析确认实体 `Process` 成为帧瓶颈，且实体间高度独立 |
| 生命周期策略相对顺序 | `StrategyIndexAttribute.Priority` 数字排序 | 数字方案简单且当前规模足够；图排序收益尚未出现 | 策略数量膨胀、多人协作频繁发生优先级冲突 |
| ActiveStrategy 同名多实现 | 策略索引全局唯一 + 每实体单实现字典 | 现有单策略内 switch 已可覆盖；分发与持久化复杂度收益不匹配 | 大量实体类型共享同一交互动词，switch 开始失控 |

## 方向一：统一树形命名空间

### 现状关系

当前 `DataSourceNode` 是“持久化文件与内存读取之间的中间产物”：文件经 `IDataSourceIoGateway` 按后缀选择 codec 解析成一棵数据树，再由 `DataSourceConverterRegistry` 转换为强类型对象。这个设计已经具备两个关键基础：

- **树形结构**：Map/Array/Text/Number/Bool/Null 六种节点构成通用数据容器。
- **codec 即插即用**：只要实现 codec 并注册后缀路由，新文件格式就能接入同一条 I/O 边界。

### 备选愿景

把“解析结果”提升为“统一命名空间根”：本地文件系统、存档 `extra/` 目录、实体数据甚至网络资源，都挂载为同一棵树上的节点。runtime 或 context 只持有受限的树根，不再暴露一组文件 I/O 接口；访问方式统一成路径导航，例如：

```
path -> to -> file -> entity -> health_point
```

其中目录、文件、文件内容、实体、实体数据键都是树上的节点，codec 只负责节点与外部字节之间的边界转换。访问范围限制可以自然地表达为“只授予某个子树的根”——越过子树即不可见，路径穿越在结构上不成立。网络访问同理：远端资源作为树的节点处理，调用方无需区分本地/远端。

### 收益

- 消除 `ISndFileAccess` / `ISndArchiveFileAccess` / `IFileMetaAccess` / `IPathResolver` 等多套路径与文件 API 之间的概念差异，策略只面对一种访问协议。
- 存档目录天然成为受限子树，`extra/` 的隔离从字符串校验升级为结构隔离。
- 同一套节点访问逻辑可以覆盖本地资源、存档资源和远端资源，测试时可整体替换树根。

### 成本与阻塞点

- **同步模型**：当前读树是同步的，本地文件可接受；一旦网络资源成为树的节点，远端读取会阻塞帧。框架的 DataSource 管线没有异步读取、取消或流式展开，补齐这些能力会贯穿 codec、Gateway、转换器和调用方。
- **内容与元数据的边界**：当前文件内容（Gateway）与文件系统结构操作（`IFileMetaAccess`）分离。合并为树后，枚举、存在性、删除、复制等语义都必须重新定义为节点操作，并继续保持“零旁路 + fail-fast”的硬边界。
- **活树生命周期**：`DataSourceNode` 目前是解析快照，统一命名空间后它是可变的活视图，需要定义缓存失效、写回、释放和部分写失败语义。
- **路由规则**：现在按文件后缀选 codec；树化后需要改为按节点能力或协议选择 codec，避免规则漂移。

### 建议的评估切片

若重新评估，先做只读的本地文件系统树（仍委托现有 `IFileSystem` 与 Gateway，作为兼容外观），验证“受限树根”是否能替代路径字符串；再让存档 `extra/` 作为子树接入；最后才处理异步远端节点。

## 方向二：实体级并发

### 现状关系

框架采用单线程帧模型：一帧内实体串行 `Process`，延迟队列负责跨帧动作。策略实例无状态且全局共享，因此策略类本身适合多线程；但实体内部的多个策略存在 `Priority` 排序，执行顺序是设计的一部分，不能把同一个实体的所有策略直接并发。

### 备选愿景

并发粒度放在**实体**而不是策略：一个实体的策略仍按优先级串行，不同实体之间可以并行。为保证安全，并发不应成为默认行为，而应作为实体的自身属性：

- 开发者显式标记某实体“可并发”，表示其逻辑已确认不依赖其他并发实体。
- 实体数据容器切换到并发模式（或使用并发安全的数据结构/分区快照）。
- 帧处理先并行执行所有并发实体，屏障等待全部完成后，再按稳定顺序串行执行剩余实体。
- 生命周期钩子、存档读写、观察者装卸、pending-kill 清理仍由框架串行编排。

### 待解决的问题

| 问题 | 风险 | 候选约束 |
|------|------|----------|
| 并发实体调用另一个实体的 ActiveStrategy | 被调用实体可能正在写自己的数据，且多个并发调用方可能同时命中同一目标 | 并发阶段不直接跨实体调用；请求记录为消息，屏障后由框架在串行阶段按稳定顺序投递/执行 |
| 并发实体读取另一个实体的 Data | 读到中间状态或过期状态 | 声明读/写键并做依赖图；或并发阶段开始时快照输入数据 |
| `SetData` 同步触发观察者回调 | 回调在并发上下文执行，破坏单线程假设 | 并发阶段只收集变更，屏障后按确定性顺序派发通知 |
| 实体间存在依赖 | 并行后结果依赖调度顺序 | 依赖边做拓扑排序；依赖实体的进程进入串行批；有环则 fail-fast |
| `Process` 中请求 spawn/kill | 容器被并发修改 | 变更先记录，屏障后由框架统一应用 |

### 为什么暂缓

策略无状态解决的是“多个实体共享策略实例”的状态污染问题，它是实体级并发的**必要但不充分**条件；真正需要重新设计的是实体 Data、跨实体调用、观察者通知和容器变更的并发契约。这个成本极高，而当前没有性能瓶颈，过早引入会把最简单可靠的帧语义复杂化。

### 重新评估信号

- 性能分析显示 `SessionManager.ProcessAllSessions` / 场景宿主 `ProcessAll` 成为帧时间主体，且热点是大量相互独立的实体计算。
- 出现大规模后台模拟或同屏单位数量达到当前串行模型无法覆盖的程度。
- 团队愿意为“可并发”实体额外声明依赖与数据访问约束。

## 方向三：生命周期策略的相对顺序约束

### 现状关系

生命周期策略的执行顺序由 `StrategyIndexAttribute.Priority` 决定：整数越小越先执行，默认 6205，同优先级按插入顺序。框架也依赖该顺序实现“低优先级产出、高优先级消费”的分层执行模式。

### 备选愿景

将“一个全局数字”改为显式约束：

```csharp
// 概念示意，当前并不存在 Before/After API
[StrategyIndex("game.action.move", Before = ["game.action.resolve"], After = ["game.intent"])]
public sealed class MoveActionStrategy : LifecycleStrategyBase { }
```

注册或插入策略时，把索引集合建成偏序图并自动求拓扑序；出现矛盾（环）立即抛异常，同批次剩余节点保持确定性顺序（如沿用插入顺序/原 Priority 兜底）。

### 收益

- 消除“默认 6205 附近应该取多少”的心智负担，团队不需要协调优先级区间。
- 顺序意图写在策略声明附近，局部可读；插件策略只需声明自己与哪些已知策略的相对位置。
- 冲突从“运行结果悄悄错了”变成“插入/注册时 fail-fast”。

### 成本与风险

- 动态 `AddStrategy` / `RemoveStrategy` 需要增量拓扑插入；当前元数据只保存索引列表，若约束来自类型特性则无需改存档格式，若允许每实体覆盖约束则需要扩展 `StrategyMetaData`。
- 传递约束可能产生开发者没有意识到的远距离排序；环检测虽可 fail-fast，但定位真实约束矛盾仍需要图诊断。
- 大规模策略集合下构图/增量排序的复杂度尚未验证；当前框架的 O(n) 插入 + O(n) 遍历成本可忽略，引入图后这部分保证会变复杂。
- 数字 Priority 对当前分层约定（感知 P4、调度 P5、行动 P6）已经足够直观。

### 重新评估信号

- 策略数量增长到需要多人/多插件协作，优先级区间冲突成为常见问题。
- 反复出现“两个策略都写了 6205，顺序靠插入顺序碰运气”导致的隐性依赖。
- 业务侧开始需要“某策略必须永远在另一策略之后”的硬约束表达。

## 方向四：ActiveStrategy 同名多实现

### 现状关系

策略索引全局唯一：一个 index 只能注册一个实现类型。`ActiveStrategyBase` 类似函数调用，由其他策略通过 `InvokeStrategy("index", input)` 主动触发。实体上挂载的主动策略容器是 `Dictionary<string, ActiveStrategyBase>`，因此每实体同一索引也只有一个实现。

### 备选愿景

让 index 从“实现名”升级为“契约名/接口名”，同一 index 可以有多个实现，由目标实体选择绑定哪一个：

- 约定 `hurt` 表示“受到攻击”这一交互接口，不同实体把 `hurt` 绑定到不同实现（护甲单位、机械单位、Boss 各有逻辑）。
- 调用方仍然 `InvokeStrategy("hurt", input)`，分发层根据目标实体的绑定表路由到具体实现。
- 支持默认实现；实体绑定缺失时回退默认，绑定冲突或实现不存在时 fail-fast。
- 绑定关系随实体元数据持久化，避免读档后接口-实现映射丢失。

### 收益

- 跨实体交互获得“面向接口编程”的体验：调用方只依赖契约，不依赖目标实体类型。
- 消除在唯一 `hurt` 策略里按物种/字段 `switch case` 的大型分发代码。
- 新实体类型只需注册自己的实现，不必修改公共交互策略。

### 成本与风险

- 策略池从 index → 单工厂 的一对一注册，变为“契约注册表 + 实现注册表 + 每实体绑定表”的三层结构。
- 每次 `InvokeStrategy` 增加一次分发查找；需要定义契约/实现命名空间，避免与现有唯一索引语义冲突。
- `StrategyMetaData` 需要记录绑定关系，存档格式和恢复校验同步扩展。
- 输入/输出类型约束弱：契约层若不强制类型签名，错误会从编译期推迟到调用期。
- 完整工具链的开发成本尚未估清：契约发现、绑定诊断、存档恢复失败定位等都要从零设计。

### 当前替代方案

在收益尚未成立时，现有能力可以覆盖：

- 在一个唯一的 `hurt` ActiveStrategy 内读取实体字段（如 `species`），按字段 `switch` 分发。
- 对生命周期行为，沿用 `*_impl` 可替换实现模式，按 data 键决定挂载哪个具体策略。
- 调用方必须知道实现索引时，也可以直接调用不同的具体索引，代价是失去统一接口。

### 重新评估信号

- 大量实体类型共享同一交互动词（`hurt` / `use` / `talk`），公共策略内的 switch 已经难以维护。
- 需要插件式实体包：新包只声明“我支持哪些契约”，不修改共享交互策略。
- 调用方代码出现大量“先读实体类型字段，再拼具体策略索引”的模式。
