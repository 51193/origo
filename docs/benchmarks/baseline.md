# TypedData 性能基线

> 本文件是 `TypedData` 源生成产物与无优化装箱实现的性能基线，作为后续性能优化的权威对照来源。
> 数值与运行环境、运行时版本强相关，跨机器不可直接比较；优化前后须在**同一环境同一运行时**下复测。

## 复现

```bash
bash scripts/benchmark.sh
```

该脚本依次运行两套基准（均标记 `[Trait("Category","Benchmark")]`，从 `ci.sh` 排除，仅此处运行一次）：

- **SG 纯净微基准** — `Origo.SourceGeneration.Tests/Benchmarks/TypedDataGeneratedBenchmarkTests.cs`
- **Core 真实模拟基准** — `Origo.Core.Tests/Benchmarks/TypedDataRealWorldBenchmarkTests.cs`

## 方法学

- **时间**：固定容量池 + 位掩码寻址（内存恒定）、大迭代次数（单轮跨多个 OS 时间片）、1 轮 warmup + 多轮取两侧各自最小耗时（剔除被抢占/GC 的离群轮）。
- **分配**：每个基准在计时轮之外，对每一侧各跑一次专用 `[MethodImpl(NoInlining)]` 测量轮，取 `GC.GetAllocatedBytesForCurrentThread()` 前后差值。测量被刻意放在独立方法里，使计时循环保留未插桩版的代码生成，避免插桩污染吞吐。
- **Alloc 列**：记每轮（即表中迭代数对应的一轮）的实测分配，格式「生成 / 装箱」。

> **「Alloc」是本基线中最稳定、最权威的信号**：跨 4 轮逐字一致。绝对吞吐受 CPU 调频与超平凡循环的代码对齐影响存在抖动（见末尾效度局限），相对趋势与分配量才是优化的可靠依据。

## Core 真实模拟基准

### 异构字典迭代（2,048,000 次 `.Data` 读取）

| 场景 | 生成 .Data (Mops/s) | 装箱迭代 (Mops/s) | 倍率 | 胜方 | Alloc 生成/装箱 |
|------|--------------------:|------------------:|:----:|:----:|----------------|
| 异构字典 `.Data` 迭代 | 412 | ~2925 | ~7.1x | 装箱 | **37.49 MB / 0 B** |

> 这是全基线最大短板，且根因被分配数据坐实：`.Data → TypedDataObjectConverter.ToObject` 对值类型**重新装箱**（数据集 ~80% 为值类型），每轮产生 37.49 MB；装箱字典直接返回已有引用（0 B、近内存带宽上限）。时间倍率本轮在 6.3–8.2x 间抖动（装箱侧是最快循环、对调频/对齐极敏感），**37.49 MB 分配是更稳定可靠的退化/改进度量**。

### 工厂构造 + 字典插入（500,000 迭代）

| 类型 | 生成 (Mops/s) | 装箱 (Mops/s) | 倍率 | 胜方 | Alloc 生成/装箱 |
|------|--------------:|--------------:|:----:|:----:|----------------|
| String  | 188 | 146 | 1.29x | 生成 | 23.53 MB / 14.97 MB |
| Int32   | 227 | 73.8 | ~3.1x | 生成 | 23.53 MB / 26.42 MB |
| Single  | 225 | 71.3 | ~3.2x | 生成 | 23.53 MB / 26.42 MB |
| Boolean | 226 | 69.3 | ~3.3x | 生成 | 23.53 MB / 26.42 MB |

> 分配揭示一处权衡：值类型插入时装箱侧多出 ~12 MB 装箱（26.42 vs 23.53），生成更快且更省；但 **String 插入生成侧反而多分配**（23.53 vs 14.97 MB）——`Dictionary<string,TypedData>` 的每个 entry 内嵌 24 字节结构体，使后备数组比 `Dictionary<string,object>`（8 字节引用）更大。生成速度仍领先，但内存占用更高。

### 观察者通知（2,000,000 迭代，两侧 0 B）

| 场景 | 生成 (Mops/s) | 装箱 (Mops/s) | 倍率 | 胜方 | 稳定性 |
|------|--------------:|--------------:|:----:|:----:|--------|
| Observer notify (old,new) + `.Data is string` | **~5400** | ~5050 | **~1.07x** | 生成 | 极稳 |

> **已优化达成持平**（见「优化记录」轮次 1）。此前装箱快 1.98x（生成 ~2790），根因是 `TryGetString` 的 `castclass`（可抛、阻断 JIT 优化）；改用 `Unsafe.As<string>` 后生成侧 ~2.81→~5.40 Gops，打平装箱。无分配差异。

### 当前优势区（优化时勿回归）

- 值类型写入 ~12–13x 且零分配、String 写入 5.2x、字典构造+插入 ~3x、混合分派 1.51x、强转链 1.41x。

## 效度局限

1. **CPU 动态调频（scaling ≈ 75%）** 引入运行间抖动；针对 ≤ 1.3x 的边际项与最快循环（如异构迭代装箱侧 6.3–8.2x、写入），建议固定频率/性能模式后复测。
2. **绝对吞吐受代码对齐影响**：写入等超平凡循环对方法布局/对齐敏感，存在 ~±8% 系统性偏移；**分配量与相对趋势不受此影响**，应作为主要判据。
3. **运行时为 .NET 10.0.9**（非目标 `net8.0`）；优化结论须在同一运行时下复测。
4. **微基准取 min-of-rounds**，偏向理想 JIT 稳态，掩盖尾延迟；真实模拟套件更具代表性。
5. 已知高方差项：String `TryGetString` 读取、混合分派、异构迭代装箱侧、值类型插入装箱侧；优化前应增加采样轮数收敛。

| 轮次 | 目标 | 改动 | 基准验证（同会话 A/B） | 全量测试 | 状态 |
|------|------|------|----------------------|----------|------|
| 1 | 观察者通知 1.98x | 生成的 `TryGetString` 用 `Unsafe.As<string>` 替代 `(string)_ref!`（去 `castclass`） | Observer 生成 2.81→**5.40 Gops**（打平）；控制项 IntRead ~551/~549、IntWrite ~917/~922 两变体一致；数组 String 读取无变化（缓存绑定） | 1613/1613 通过，覆盖率门禁达标 | ✅ 已 ship |

## 结论与已知结构性限制

目标是「让生成代码在基础值类型与常见的 `string` 上至少与 Naive 装箱实现持平或无显著劣势」。按本基线评审结论如下：

- **值类型目标已达成。** 值类型读取均在 **≤ 1.10x**（Int32 1.05x、Boolean 1.10x 等），属「无显著劣势」；写入（~12–13x，零分配）、混合分派（1.51x）、强转链（1.41x）、字典构造+插入（~3x）远超装箱。
- **`castclass` 移除（`Unsafe.As<string>`）对「操作绑定」的 `TryGetString` 热路径有效（已采纳），对「缓存绑定」的数组 string 读取无效（结构性）。**
  - **Observer 通知（操作绑定）**：生成 2.81→**5.40 Gops**，打平装箱（`castclass` 可抛、阻断 JIT 优化；`Unsafe.As` 无副作用可被优化）→ **已 ship**（见优化记录轮次 1）。
  - **数组 String 读取（缓存绑定）**：10 轮中位仅 408→418 Mops/s（+2.5%，噪声内），仍 ~1.40x → 受 **24 字节结构体**缓存成本主导（`_ref`@偏移16 比值类型 `_inlineBits`@偏移8 更易跨缓存行）。
  - **DictLookup 值类型**（`TryGetInt32` 等，无 `castclass`）不受此改动影响，仍 1.33–1.41x → 结构性（`Dictionary<string,TypedData>` 每 entry 40 字节 vs 装箱 24 字节 + 24 字节结构体按值拷贝）。
- **24 字节是当前 GC 安全设计的下限。** `long _inlineBits` 与 `object? _ref` 不能重叠（GC 要求托管引用槽独立扫描），`byte _kind` 无空闲位可塞。压到 16 字节需牺牲 `long`/`double` 的满 64 位内联，或引入额外分支/类型查找（多半不划算），且改动 `internal` 的 `_kind/_inlineBits/_ref` 布局（被生成代码与测试经 `InternalsVisibleTo` 依赖）——属高风险、低把握的内部接口/布局变动。**评审决定：接受现状，不做此重设计。**
- **异构 `.Data` 迭代（装箱快 ~7.1x、生成 37.49 MB/轮）属语义性装箱**：`.Data` 的返回类型是 `object`，值类型必然装箱；这是 API 形态决定的，不在「`TryGet` 持平」目标范围内。若需消除，须提供按 `Kind` 分派的无装箱访问 API（另行评估）。

> 因此除非未来对 `TypedData` 存储模型做架构级重设计，String 读取的 ~1.40x 视为**已知结构性下限**而接受。后续若有针对该项的优化提案，须先在本基线同口径复测验证（≥ 8 轮收敛），再决定取舍。
